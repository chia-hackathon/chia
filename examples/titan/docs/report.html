Titan：在 Saturn 向量單元上實作 RISC-V IME 矩陣擴充

Titan 以 CHIA agentic loop 在 Chipyard 樹內、Shuttle 核心的 Saturn 向量單元上實作 RISC-V IME（Zvvm）v0.9.0 矩陣擴充，目標是邊緣端 LLM 的 INT8 GEMM。三輪下來交付 15 條規格指令中的 8 條，並附一份獨立撰寫、先於 RTL 存在的 Spike 參考模型。整個專案的形狀不是「agent 寫硬體」，而是「先把裁判造出來，再讓被告受審」：46 小時、837 美元的支出中，絕大部分花在發現迴圈與裁判本身必須長成什麼樣子，真正用它來交付功能的那幾輪只佔很小一塊。最有價值的結果也不是那 8 條指令，而是一個方法學上的發現——模擬器的隨機暫存器初始化讓「邏輯上完全無作用的改動」也能翻轉測試結果，因此本專案早期好幾個關於同一個缺陷的實驗（包括第一輪那個被當成根因的一行修正）都是被混淆的。

規格 Zvvm v0.9.0 參數 VLEN=256 · DLEN=128 · Shuttle 最終產物 titan_runs/r15_round3.diff 資料截止 2026-09-17
一 · 迴圈骨幹與最終計數

五個階段，依照它們真正執行的順序

階段編號在這裡有意義，因為順序本身承載了專案的核心原則：每一個裁判都先於它所審判的對象存在。rvv_ref.py 由人類在任何 RTL 存在之前寫成；riscv-vector-tests 隨 Saturn 附帶、在任何人動手之前就已通過；Spike 模型先跑，所以模型作者不可能看過它稍後要審判的 RTL。以下是 8 指令設計的最終驗證計數。

Stage M 模型 80 / 80 agent 的 Spike 模型 對 rvv_ref.py；此時尚無 RTL
Stage S1 定向測試 80 / 80 RTL 對 rvv_ref.py，雙發射 DIRECTED_CONFIG
Stage S2 RVV 回歸 837 / 0 RTL 對 stock Spike lockstep cosim；837 執行、0 失敗
Gate 全幾何掃描 548 / 548 每一組合法的 (SEW, λ, LMUL, VL)，含部分 VL
Stage S3 隨機 lockstep 64 / 64 隨機化 tile 幾何，RTL 對 agent 自己的 Spike 模型

來源：r15_full_verify/results.json（directed 80/80、s2_full 837 執行 / 0 失敗）與執行 r15_0917_1109（20260917_122552_gate.json 548/548、20260917_123203_summary.json stress_done: 64、converged: true）。S2 在迴圈內跑的是 150 支的等距抽樣（r15 為 0/150）；上表的 837 是迴圈外補跑的全套 —— 841 支扣掉 4 支已記錄的排除項。

三 · 方法

迴圈、兩個互相隔離的 agent，以及回饋紀律

迴圈是嚴格循序的：Stage M 通過 → S1 與 S2 一起通過 → Gate → S3 跑到期限且無分歧，全部成立才標記 converged。S1 與 S2 不是兩個前後相接的階段而是同一個迴圈，理由寫在 titan_loop.py 的 docstring 裡：一次弄壞了普通 RVV 的 directed pass 不算 pass。每次嘗試的流程是編輯 → 以 DIRECTED_CONFIG 建置（不含 cosim harness，因為 S1 不得依賴 Spike）→ 跑 directed → 乾淨的話才建一次 COSIM_CONFIG 並跑 RVV 回歸抽樣，兩者必須在同一次嘗試裡都乾淨才回傳成功。

兩個 agent 完全分開。Stage M 的模型 agent 以 resume_session=True 保留整個階段的對話，但沒有任何自助建置或測試工具，只有 driver 每回合替它建置與評分一次；它被明文禁止讀取 generators/saturn/ 底下任何東西，也禁止讀 rvv_ref.py、ime_tests.py、ime_stress.py、sim_check.py。S1/S2 的 RTL agent 則每回合換一個全新 session，可以編輯 Saturn 與 rocket-chip 的 VType/VConfig 部分，並持有自助的建置測試工具。這個隔離不是只靠 prompt 規則，而是靠順序：模型寫在前面，那時候根本沒有 RTL 可抄。

agent 每回合看得見的東西是刻意設計過的：依 outcome / EMUL_C / LAMBDA / SEW / LMUL 分組的 directed 結果（而不是按指令分組）、失敗 RVV 測試的名字（上限 40 個）、自己的持久筆記，以及在 mismatch 時最多 6 筆帶實際數值的證據與 tile dump。看不見的是參考模型的原始碼、測試產生器、以及編碼推導。回饋只包含自檢程式在執行期印出的東西，從不包含黃金模型的程式碼。

順序保證模型 agent 不可能讀到 RTL。它不保證模型 agent 不去讀測試——而在第一輪，測試本身就帶著缺陷。模型 agent 明知 Sail 附錄怎麼寫，仍在註解中寫下「測試提供的佈局只有在採用散文解釋時才得到正確結果，所以我們這裡跟隨散文」，然後照著壞掉的測試把模型擬合上去。兩個互相自洽的錯誤產物，從迴圈內部是偵測不到的。修正之後才加入常設規則：「可執行的 SAIL 附錄是規範性的……如果一個測試失敗，而你能想到唯一讓它通過的方法是寫下 SAIL 沒說的東西，那就停下來，不要寫。」

六 · 缺陷

九個缺陷，依撞上的順序

每一則的格式相同：症狀 → 如何定位 → 成因 → 修法 → 代價。成本取自帳本與 trace。注意 §6.3 與 §6.4 在 r4、r5 同時存在，兩者的金額不可相加。

6.1 · 迴圈 harness

S1 用 cosim config 建置 directed 映像

r3 · ~0:56 · $32.96
症狀
Stage M 乾淨收斂（三輪 27/27）之後，S1 在 attempt 1 回傳 27/27 trap，attempt 2 在完全不同的 RTL diff 上回傳位元相同的 27/27 trap。
定位
均勻失敗的簽名（狀態檔沒有任何 LAMBDA/SEW/LMUL 分佈）指向 harness 而非設計。agent 自己誤判為 vtype.lambda 解碼的 WARL clamp bug，整個 attempt 2 花在一個注定不可能贏的實驗上。
成因
S1 的 directed 映像用 COSIM_CONFIG 建置。cosim config 連結的是容器映像裡的 stock libriscv，它從未聽過 Zvvm；directed 程式是自檢的、不需要黃金模型，但 cospike 會在第一個帶 lambda 欄位的 vtype 寫入時中止，發生在任何程式印出結論之前。
修法
r4 起 SYNTH_CONFIG as DIRECTED_CONFIG，S1 用它建置，S2 在 directed 通過後才獨立建 COSIM_CONFIG。同一份修改加入 _dump_sim_logs，因為 r3 完全沒留下「為什麼 27/27 trap」的觀察管道。
6.2 · 迴圈排程

Ray placement-group 死鎖，3 小時 50 分

r2 · 3:50:11 空轉 · $0
症狀
4:14:18 wall、1 次 LLM 呼叫、$11.44、未收斂。Stage M 的 LLM 回合正常結束，之後的一切都掛住。
定位
trace 有 127 個事件，build_spike 完成到 run_end 之間是 13,811 秒（230.2 分鐘）的空窗，零事件；然後 27 個 spike_run 配對在 6–9 毫秒內全部觸發並完成。關鍵在於 profiler 的 dispatch 與 complete 都是 worker 端在執行時才發出，所以一個 Ray 從未排程的任務在真正跑起來之前什麼都不會記錄——正確的說法是「從未被排程」，不是「從未被 dispatch」。
成因
_run_on_spike 少了 pg_opts，27 個 spike_run 任務向節點的預設資源池要 chipyard，而 STRICT_PACK 的 placement group 早已把它整個預約走。任務永遠停在 PENDING_NODE_ASSIGNMENT，而 Ray 對這種情況從不報錯。
修法

七 · 方法學上的主結果

隨機暫存器初始化是一場每次建置重抽的樂透

這一節自成一節，因為它改寫了前面好幾則缺陷敘事的效力。

模擬編譯時帶著 +define+RANDOMIZE_MEM_INIT / _REG_INIT / _GARBAGE_ASSIGN / _INVALID_ASSIGN。FIRRTL 因此為每個模組發出一個 initial 區塊，把偽隨機位元打包進每一個沒有 RegInit 的暫存器。打包方式取決於暫存器寬度，所以任何一個暫存器寬度的改變，都會把同一模組中排在它後面的每一個暫存器的初始值重抽一次。

這件事是在第三輪一個對照實驗裡直接被看見的。當時要驗證的假設很簡單：把一個完全無作用的 no-op 功能單元加進 integerFUs，會不會弄壞 .vf 測試？加進去之後 ExecuteSequencer.fu_sel 從 7 位元變 8 位元，發出的邏輯完全相同（fu_sel <= {1'h0, <同一個運算式>}），但隨機化區塊整個位移：

- fu_sel = _RANDOM[5'h14][22:16];    + fu_sel = _RANDOM[5'h14][23:16];
- eff_vl = _RANDOM[5'h14][31:23];    + eff_vl = {_RANDOM[5'h14][31:24], _RANDOM[5'h15][0]};
- eidx   = _RANDOM[5'h15][21:14];    + eidx   = _RANDOM[5'h15][22:15];

然後 machine_vfsgnjn_vf-1 在一個組合邏輯完全沒有改變的設計上分歧了。把隨機化 define 拿掉之後，同一個分支是乾淨的。

結果

這個 bug 上的每一個更早的實驗都是在這場樂透底下跑的——包括第一輪那個被當成根因的一行「修正」、issue_decouple 的 A/B/C 篩選，以及整個檔案層級的 rtl_bisect。這也解釋了為什麼一個「修正」曾經有效、後來又失效，以及為什麼二分定位會得出一個「不可再約化的核心」這種答案。

把混淆移除之後重跑，結論有兩層。第一層是那個 no-op 功能單元的實驗通過了：加寬 integerFUs 並不會弄壞 .vf；而 IME 設計本身不是樂透的受害者，它在隨機化開與關之下都是 4/4 失敗，bug 是真實且決定性的。

第二層才是真正的發現。在確定性的條件下把 IME diff 逐段拆解，沒有任何一個子系統是必要的：移除矩陣 FU、或 tile 載入儲存路徑、或 vtype/lambda 擴充、或 EarlyDecode、或 PipelinedFaultCheck、或 mem/ 的改動，各自單獨做，四支探針全都還是失敗；而 vtype 擴充單獨套用在乾淨樹上完全乾淨。更關鍵的是，兩個架構行為完全相同的分支給出相反的結果——C1 強制 is_tile_op 為假（這已經蘊含 C3 的效果）卻 4/4 失敗，而效果是其嚴格子集的 C3 卻 0/4 通過。

最終採用的改動是把 MatrixMacc 與 MatrixW 從 backend/ExecuteSequencer.scala 裡共用的 dis_ctrl 欄位清單移出，放進它們自己的 VectorDecodedControl。它被選中的理由是：它是唯一一個能讓八條 IME 指令全部保持功能的通過分支（C3 會破壞 tile 載入儲存，C4 直接移掉兩個 IME 功能），而且有一個說得通的解讀——它把共用的 sequencer 解碼表還原成乾淨 Saturn 上的原樣，於是最小化器對該表 don't-care 區域的解法也回到原樣。

誠實的結論

清乾淨 150 支中的 150 支，不是一次幸運重排合理做得到的事，所以這是「修好了」的證據，而不只是抽到好籤的證據。但它仍然是一次邊際移動，不是被證明的根因。真正根因版本的解釋（讓每個欄位遵守自己宣告的預設值而不是 don't-care）在實驗中沒有修好探針。潛在的缺陷還在：.vf 純量（frs1）的遞送路徑——整個設計裡唯一晚一級才抵達 Saturn 的純量——是邊際的，乾淨的 Saturn 與修正後的 Saturn 都是靠排程的運氣通過它，而不是靠構造保證。向量後端未來的任何改動都可能重新觸發它。

方法學上的推論很直接：四支探針的分支無法區分「一個修正」與「一次有利的重排」，只有夠廣的測試集可以；而這個 bug 上未來的每一次 A/B 都必須關閉隨機化，否則結果不可重現。

四筆 S2 排除項，以及為什麼每一筆都有原則

被排除的是 machine_vfcvt_f_x_v-0、machine_vsetvl-0、machine_vsetivli-0、machine_vsetvli-0。第一筆是真正的既存基準失敗：乾淨的 Saturn 對 stock Spike 本來就有 1 ulp 的差異。後三筆是同一類，而且理由更強——IME v0.9.0 要求一條 IME-legal 的 vsetvli 必須把非零的 λ 寫進 vtype[62:60]，而 stock Spike 不認識這個欄位、永遠回 0，所以任何符合規格的 IME 實作都不可能讓這些測試在 stock Spike 之下通過。分歧的特徵是 spike x14 = 0x5 對 DUT x14 = 0x3000000000000005，也就是 λ=0b011，VLEN=256 / SEW=8 之下的最大合法值。

原則因此是：一個正確的實作在這個裁判下不可能通過的測試，要移交給能夠審判它的裁判，而不是刪掉。vtype 的 IME 欄位語意改由 Stage 3 以 IME Spike 模型 lockstep 判定。這個排除也是刻意要防止 agent 用「破壞規格相容性」的方式去修掉症狀——先前一次把 λ 強制為 0 的 agent 改動被丟棄了。
