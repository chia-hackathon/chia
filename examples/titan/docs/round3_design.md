Encoding-map note (spec 1259–1262): on funct6 0x39/0x3a/0x3b, `vm=1` selects the
integer-accumulate form and `vm=0` encodes `vfwimmacc.vv` / `vfqimmacc.vv` /
`vf8wimmacc.vv`. So rows 5, 6 and 13–15 share funct6 and are split by one bit;
`ime_encodings.check_mx_split` pins that and round three implements only `vm=1`.

## 2. Batch decision

**Round three = `vwmmacc.vv`, `v8wmmacc.vv`, `vmttl.v`, `vmtts.v`** (4 → 8 of 15).

1. W=2/W=8 are the round-two datapath at another packing depth: vtype.SEW is
   still the accumulator width, tiles still arrive through `vmtl.v`, and only
   funct6 and the per-storage-element unpack change — near-zero incremental RTL
   over the existing MAC array, and it closes Zvvmm.
2. The transposing pair is one Sail line different from the order-preserving pair
   (`(i % linesize)*LD + (i / linesize)` vs `(i / linesize)*LD + (i % linesize)`)
   and two encoding bits (27:26 = 0b01 vs 0b00), with `flat_idx = tile_reg_idx(...)`
   character-identical — it reuses the whole tile-load path and adds an address
   generator, not a format.
3. Edge-LLM INT8 value: the transposing pair removes the software repack for a
   row-major B (or a column-major A/C) — spec's own table at 2999–3004 — which is
   the dominant non-MAC cost in a tiled INT8 GEMM. W=2/W=8 add Int8→Int16 and
   Int8→Int64 accumulation ranges around round two's Int8→Int32.
4. Risk is bounded and *targeted at the known cluster*: round one's bugs were in
   tile layout, so the transposing tier is generated over the full
   SEW/LAMBDA/LMUL/N sweep, and `sim_check.check_transposing_is_load_bearing`
   proves all 27 full-VL transposing programs fail if the transpose is ignored.
5. **The Zvvfmm family waits — explicitly — until PPA and the transposing loads
   are done.** It buys nothing for the stated INT8 goal, and it needs an FP MAC
   array, `altfmt` format decode, `frm`/`fflags`, the G/psm/rnd accumulation and
   rounding model, plus MX scale decode: all of it lands in the shared int/fp
   issue path where round one's other bug cluster lived.
6. Corollary: the three MX integer-input forms (13–15) are FP-accumulate
   instructions wearing integer opcodes, so they inherit the FP deferral.

## 4. Encodings used

From `specs/ime/instructions.json`; `ime_encodings.check_round_three_bits`
re-derives each from the wavedrom blocks at spec 7067 (`vwmmacc.vv`),
5414 (`v8wmmacc.vv`), 6674 (`vmttl.v`), 6830 (`vmtts.v`).

| Mnemonic | opcode | funct3 | vm | funct6 / variant | sample word |
|---|---|---|---|---|---|
| `vwmmacc.vv v24, v0, v8` | OP-V 0x57 | OPIVV 0 | 1 | funct6 0x39 | `vwmmacc.vv v4,v8,v12` = `0xe6c40257` |
| `v8wmmacc.vv v24, v0, v8` | OP-V 0x57 | OPIVV 0 | 1 | funct6 0x3b | `v8wmmacc.vv v4,v8,v12` = `0xeec40257` |
| `vmttl.v v4,(a0),a1` | 0x07 (load) | 0b111 | field | bits 27:26 = 0b01, bit 28 = 1, lambda[31:29] | `0x16b57207` |
| `vmtts.v v4,(a0),a1` | 0x27 (store) | 0b111 | field | bits 27:26 = 0b01, bit 28 = 1, lambda[31:29] | `0x16b57227` |

`encode('vmtl.v',…) ^ encode('vmttl.v',…) == 1 << 26` exactly, and likewise for
the store pair — asserted in `check_round_three_bits`.

## 6. Numbers

- Byte-identical regression: the round-one+two tiers under the new code give
  sha256 `842e6c441d7b593ab654f1b629d9b5b0678040142c1c98ed01abfa40c9caddeb`
  (34 programs, per-iteration) and
  `90347083f70ffaa7976844d235ca3b0f96ef9773fff91709ffaf49b663ea95ef`
  (244 programs, gate) — identical to the pre-change values, both when scoped
  via `insns=` and as the leading prefix of the full suite.
- Per-iteration suite: 34 → **80** (27 W=1/op + 27 W=1/t + 14 W=2/op + 7 W=4/op + 5 W=8/op), 162,344 lines.
- S1 gate: 244 → **548** (200 + 200 + 88 + 44 + 16), 1,357,476 lines.
- `sim_check.py`: 732/244 → **1644 executions across 548 geometries, 0 failed**
  (~19 s). 5 negative controls (one per tier) + `check_transposing_is_load_bearing`.
- New geometry names: `ime_w_sew{16,32}_*`, `ime_8w_sew64_*`, `ime_t_sew{8,16,32,64}_*`;
  stress names gain `_w2`/`_w8` and `_t`.
- `describe()` gains a trailing ` TL=t` clause for transposing geometries, after
  `EMUL_C`, so `helpers._GEOM_RE`'s three adjacent `VLEN=/SEW=/LAMBDA=` fields
  are untouched (asserted in `check_widening_verdict_geometry`).
