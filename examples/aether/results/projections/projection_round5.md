# Llama-3.2-1B round5 projection vs round4 / roofline

Generated by `loop/llama_project.py` against `measured_cycles_round5.json` (new
in this task), which is `measured_cycles_round4.json` plus one change: the
`int8_gemv_gemmini` entry's **N=16** `additional_measurements` point (the
pristine `llama-q8-gemv-gemmini-n16` batched-decode GEMV tile, never
previously optimized) moves from 168,367 -> 142,458 cycles. All commands use
`--device int8_gemv=gemmini --device lm_head_gemv=gemmini`, same as
round2-round4 (see `_README` in the measured-cycles JSON). Raw command output
is under `out/llama-profile/proj_round5_{decode,prefill}.txt`.

Cost basis: **round4** = fourth optimization pass (`measured_cycles_round4.json`).
**round5** = fifth optimization pass, this report (`measured_cycles_round5.json`).
**roofline** = `max(compute, memory)` lower bound, no fudge factor. Clock is
**1.00 GHz** (`clock_hz: 1000000000.0` in the measured-cycles JSON / `--clock-ghz`
default 1.0) throughout, unchanged since round2 — the same constant used for
every tok/s figure in `projection_round4.md`, so round5's numbers below are
directly comparable to it.

```
python -m loop.llama_project --scenario decode --S 512 \
  --measured out/llama-profile/measured_cycles_round5.json \
  --device int8_gemv=gemmini --device lm_head_gemv=gemmini

python -m loop.llama_project --scenario prefill --N 64 \
  --measured out/llama-profile/measured_cycles_round5.json \
  --device int8_gemv=gemmini --device lm_head_gemv=gemmini
```

**Important note on scope:** round5's only touched kernel is
`llama-q8-gemv-gemmini-n16`. Neither `--scenario decode` (which projects one
token at a time, N=1) nor `--scenario prefill` (which uses the `int8_gemm`
M=64 tile) ever reads the N=16 GEMV shape — `MeasuredDB.load` keys one
`Measurement` per kernel name, and the N=16 point lives only as a
documentation-only `additional_measurements` entry under `int8_gemv_gemmini`
(see `_README`'s "HOW TO SWITCH..." section and the entry itself). So (a)-(d)
below are **byte-for-byte identical to round4** — confirmed by diffing
`proj_round5_{decode,prefill}.txt` against `proj_round4_{decode,prefill}.txt`,
zero differences — and (c) is a repeat of round4's numbers, not a new
measurement. Section (e) is where round5's real result lives: `llama_project.py`
has **no CLI flag or config path for a batched (N>1) decode scenario** (its
`--scenario` choices are only `decode`/`prefill`, `--S` is decode context
length and `--N` is prefill tokens-per-pass, and the N=16 GEMV entry is
explicitly marked "documentation only" in `_README`), so the batch-16 decode
comparison is computed manually there instead of via the script.

## (e) N=16 batched decode — manual comparison (script has no batch-decode mode)

`llama_project.py --help` confirms `--scenario` accepts only `decode` or
`prefill`; `--S` is "decode: KV cache length the new token attends to" and
`--N` is "prefill: tokens per pass" — there is no batch-size flag for decode,
and no config path that feeds the N=16 GEMV shape into `project()`. So this
section is computed by hand from `measured_cycles_round5.json`, using the
same 1.00 GHz clock as every other number in this document (`tok/s = 1e9 /
cycles_per_token`).

**n1 kernel** (`llama-q8-gemv-gemmini-n1`, one decode token per invocation):
verified against `measured_cycles_round5.json`'s `int8_gemv_gemmini` top-level
entry (unchanged since round2) — **132,424 cycles/token**, matching the task's
assumed value exactly (no discrepancy found).

**n16 kernel** (`llama-q8-gemv-gemmini-n16`, 16 decode tokens per invocation,
this round's result): **142,458 cycles per invocation / 16 tokens = 8,903.6
cycles/token**.

| | cycles/token | tok/s (this GEMV kernel alone, 1.00 GHz) |
|---|---:|---:|
| n1 (serial, 1 token/invocation) | 132,424 | 7,551.3 |
| n16 (batched, 16 tokens/invocation) | 8,903.6 | 112,309.4 (aggregate, all 16 sequences) |
| n16, per-sequence | 8,903.6 | 7,019.3 (per individual sequence in the batch) |

- **Aggregate throughput ratio:** 112,309.4 / 7,551.3 = **14.87x** more total
  decode-GEMV throughput running 16 sequences batched through `n16` than
  running the same 16 sequences serially through `n1` (132,424 x 16 =
  2,118,784 cycles for 16 tokens serially, vs 142,458 cycles batched — the
  same 14.87x falls out either way).
- **Per-sequence rate:** an individual sequence inside the N=16 batch actually
  advances *slightly slower* per-token (7,019.3 vs 7,551.3 tok/s, a 0.93x
  ratio) than it would running alone via `n1` — batching trades a small
  per-sequence latency cost (12% more cycles per invocation, 168,367/16 vs
  150,339 pristine, or 142,458/16 vs 132,424 post-round5) for a large
  aggregate-throughput win, exactly the "16x the arithmetic for 12% more
  cycles" relationship `measured_cycles_round4.json`'s `_README` already
  documented for the *pristine* N=16/N=1 pair; round5's optimization pass
  narrows both numbers (168,367->142,458 and, unrelated to this round,
  132,424 stays put) without changing that qualitative story.
- **This is a standalone-kernel comparison**, not a full end-to-end model
  tok/s projection — `llama_project.py`'s `decode`/`prefill` scenarios do not
  model batched decode (attention, norms, MLP etc. would also need a batch
  dimension to project a true N=16 end-to-end number), so it should not be
  read against the 6.260 tok/s end-to-end figure in (a).
