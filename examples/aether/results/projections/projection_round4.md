# Llama-3.2-1B round4 projection vs round2 / round3 / roofline

Generated by `loop/llama_project.py` against `measured_cycles_round4.json` (new in
this task) plus the existing round2/round3 files, all with
`--device int8_gemv=gemmini --device lm_head_gemv=gemmini` (the GEMV path this
project has used since round1: Gemmini is 4.1-4.7x faster than the naive Saturn
RVV baseline for the N=1 decode GEMV; see the `_README` in the measured-cycles
JSON). Round1 columns are dropped from the comparison tables below, same as
round3's report dropped round0 — see `projection_round3.md` if round1/round0
numbers are needed. Raw command output for round4 is under
`out/llama-profile/proj_round4_{decode,prefill}.txt`.

Cost basis: **round2** = second optimization pass. **round3** = third
optimization pass. **round4** = fourth optimization pass, this report
(`measured_cycles_round4.json`). **roofline** = `max(compute, memory)` lower
bound, no fudge factor.

`loop/llama_project.py`'s `--mem-bytes-per-cycle` now **defaults to 8.0**
(the corrected Gemmini mbus bandwidth; confirmed via
`grep -n mem-bytes-per-cycle loop/llama_project.py` -> `default=8.0`). Round3
needed an explicit `--mem-bytes-per-cycle 8.0` override mid-report to get a
corrected roofline scenario (see `projection_round3.md`'s "2026-09-09
roofline 修正" section); round4 needs no override at all — **round4 is the
first round whose numbers (projected AND roofline, not just roofline) are
measured and computed entirely under the corrected 8 B/cycle mbus
assumption**, using the commands:

```
python -m loop.llama_project --scenario decode --S 512 \
  --measured out/llama-profile/measured_cycles_round4.json \
  --device int8_gemv=gemmini --device lm_head_gemv=gemmini

python -m loop.llama_project --scenario prefill --N 64 \
  --measured out/llama-profile/measured_cycles_round4.json \
  --device int8_gemv=gemmini --device lm_head_gemv=gemmini
```

**Important caveat this creates for prefill only:** prefill's `lm_head_gemm`
kernel is still unmeasured (`cycles: null`), so its contribution to the
"projected" total is `roofline x --fallback-factor(4)`, not a real
measurement. Because round3's *raw* `proj_round3_prefill.txt` was generated
before the 8 B/cycle default landed, its `lm_head_gemm` estimate is still
built on the *stale* 16 B/cycle roofline (1.03M cyc/tok = 257.01k x 4); round3's
own report only patched the **roofline column** by hand to the corrected
value (514.03k) without regenerating the "round3" projected column. Round4's
`lm_head_gemm` estimate, by contrast, is built on the now-default corrected
roofline (2.06M cyc/tok = 514.03k x 4) throughout. Diffing the two raw files
confirms this is the *only* thing that changed besides the real `int8_gemm`
kernel improvement — every other measured prefill operator's cyc/tok is
byte-for-byte identical between `proj_round3_prefill.txt` and
`proj_round4_prefill.txt`. So the naive round4-vs-round3 prefill delta below
looks like a regression; it is a unit-basis artifact of an unmeasured
placeholder doubling, not a real kernel change, and section (c) below
isolates the real effect.

## (c) Round4 vs round3 speedup

- **Decode: 1.0003x** tok/s (6.258 -> 6.260 tok/s; 159.80M -> 159.73M
  cyc/token) — essentially flat, for the same reason as round2->round3:
  `int8_gemv` (76.9% of decode share) is untouched and fully converged
  (still 132,424 cycles, deliberately only probed for 2 iterations this
  round). The tiny real gain comes entirely from `lm_head_gemv`'s ratio-scaled
  entry moving 113,978 -> 113,727 (0.3M cyc/token less at 17.8% share),
  because the *dedicated* lm_head tile kernel improved marginally
  (635,908 -> 634,507, 1.002x).
- **Prefill: nominally 0.867x** tok/s (156.006 -> 135.312) but this is an
  artifact, not a regression — see the caveat above. The **real** change is
  `int8_gemm`'s second optimization pass (138,892 -> 137,246 cycles, 1.012x
  faster, 62.8%/53.9% prefill share before/after the mbus-fix reweighting),
  which on an apples-to-apples basis with round3's methodology gives
  **~1.008x** faster prefill (156.006 -> ~157.2 adjusted tokens/s).

Round4's headline story is really about `lm_head_gemv_gemmini`'s dedicated
tile and `int8_gemm`, both getting further (smaller, diminishing-returns)
optimization passes, while `int8_gemv_gemmini` — per the Round 4 planning
note in `out/loop/README.md` — was deliberately only probed (2 iterations)
rather than fully re-searched, since round3 had already converged it to
~1.01x roofline.

## (d) Biggest remaining gap to roofline

**Decode: `int8_gemv`, unchanged from round3, essentially at its floor.**
Still 122.89M cyc/token against the 121.86M roofline, a ~1.03M-cycle
(1.008x) gap — unchanged in absolute terms from round3 (round4 spent only 2
probe iterations on it and found nothing new, as expected: it remains
DMA-bound at ~7.92 B/cycle of the real 8 B/cycle mbus peak, ~99%). Same
conclusion as round2/round3: further decode gains need batching decode GEMVs
(more useful compute per byte moved), not more per-kernel tuning at N=1.

**Prefill: `lm_head_gemm`, still the largest nominal gap, but now trivially
so by construction** — it is an *unmeasured* `roofline x 4` placeholder, so
its "gap" to roofline is definitionally always ~4.00x (2.06M vs 514.03k this
round, was 1.03M vs 257.01k last round — same 4x ratio, just measured
against the now-doubled roofline). This is not new information; it just
restates that `lm_head_gemm` has never been measured, since round0.
**The largest gap among kernels that are actually measured is still
`int8_gemm`**: 3.98M cyc/token vs a 3.80M roofline, 1.047x the floor (down
from round3's 1.060x, ~0.03M-cycle narrower) — unaffected by the mbus fix
since it is compute-bound. Measuring the real `lm_head_gemm` kernel remains
the single highest-value remaining gap in prefill, as it was in round3.

### lm_head_gemv_gemmini conversion (round3 -> round4)

Same method as round2 and round3 (see `projection_round3.md`'s "lm_head_gemv_gemmini
conversion (round2 -> round3)" section for the full rationale): `llama_project.py`
extrapolates `lm_head_gemv_gemmini` linearly in MACs from its measured tile
(`work_measured=1,048,576` MACs, the M=512/K=2048 `n1` shape) up to the full
128,256x2,048 lm_head, so the dedicated lm_head-tile kernel's raw cycle count
(a *different* tile shape, M=2048/K=2048) cannot be substituted directly
without breaking that basis's self-consistency.

Round4 re-optimized the dedicated lm_head tile kernel
(`llama-q8-gemv-gemmini-lmhead`, run_id `20260909-200541-dae1`, seeded from
round3's best, 12/12 iterations, no restart): round3's best 635,908 ->
round4's 634,507 cycles (0.997797x, i.e. only 1.002x faster — a much smaller
gain than round3's own 1.164x-vs-baseline improvement, consistent with the
Round 4 planning note's hypothesis (`LQ8_B_ROWS` 4->16) not paying off as
hoped: this kernel is nearing its own floor too).

As in round2/round3, we carry the same fixed round1 n1-basis value (132,653
cycles at 1,048,576 MACs) forward, scaled against the **original pre-round1
tile baseline** (740,101 — the same baseline round3 used, NOT round3's
635,908 result) by the lm_head tile's cumulative best-to-date improvement
ratio:

```
ratio  = 634,507 / 740,101 = 0.857325
round4 = 132,653 * 0.857325 = 113,726.72 -> 113,727 cycles   (at work_measured = 1,048,576)
```

The raw M=2048 tile numbers (740,101 baseline, 635,908 round3, 634,507
round4) and the round1/round2/round3 history are kept in the entry's
`additional_measurements` for reference; they are documentation only and are
not read by `llama_project.py` (`MeasuredDB.load` keys one `Measurement` per
kernel name, matched against this entry's own `work_measured`/shape).
