# Llama-3.2-1B round3 projection vs round2 / round1 / round0 / roofline

Generated by `loop/llama_project.py` against `measured_cycles_round3.json` (new in
this task) plus the existing round0/round1/round2 files, all with
`--device int8_gemv=gemmini --device lm_head_gemv=gemmini` (the GEMV path this
project has used since round1: Gemmini is 4.1-4.7x faster than the naive Saturn
RVV baseline for the N=1 decode GEMV; see the `_README` in the measured-cycles
JSON). Raw command output for round3 is under
`out/llama-profile/proj_round3_{decode,prefill}.txt` (round0/1/2 outputs were
already present from the previous task).

Cost basis: **round0** = pristine naive-RVV/Gemmini baselines (`measured_cycles.json`).
**round1** = first optimization pass. **round2** = second optimization pass.
**round3** = third optimization pass, this report (`measured_cycles_round3.json`).
**roofline** = `max(compute, memory)` lower bound, no fudge factor.

## 2026-09-09 roofline 修正

Gemmini 的權重/激活流量實際走 rocket-chip 的 mbus（`MemoryBusKey =>
MemoryBusParams(beatBytes = 8)`），只有 **8 B/cycle**，不是先前假設的走 sbus/DMA
port 頻寬 **16 B/cycle**（`WithSystemBusWidth(128)`，Gemmini `dma_buswidth`）。
`loop/kernels.py` 已在同日修正各 kernel 的 `roofline_cycles`：

| kernel | 舊 roofline cycles (16 B/c) | 新 roofline cycles (8 B/c) |
|---|---:|---:|
| llama-q8-gemv-gemmini-n1 / -n16 (GEMV, 1 MiB 權重) | 65,536 | 131,072 |
| llama-q8-gemv-gemmini-lmhead (GEMV, 4 MiB 權重) | 262,144 | 524,288 |
| llama-q8-gemm (M=64/K=2048/N=256, compute-bound) | 131,072 | 131,072（不變） |

`loop/llama_project.py` 的 end-to-end roofline 是用同一個假設，透過
`--mem-bytes-per-cycle`（預設 16.0）的 `max(compute, memory)` 公式算出來的，
與上表的 kernel 級 roofline 是同一套物理假設。用同樣的 measured-cycle 檔案
（`measured_cycles_round3.json`）與 device 對應，只把 `--mem-bytes-per-cycle`
從預設 16.0 改成 8.0 重跑，得到修正後的 roofline 情境：

```
python -m loop.llama_project --scenario decode --S 512 \
  --measured out/llama-profile/measured_cycles_round3.json \
  --device int8_gemv=gemmini --device lm_head_gemv=gemmini \
  --mem-bytes-per-cycle 8.0

python -m loop.llama_project --scenario prefill --N 64 \
  --measured out/llama-profile/measured_cycles_round3.json \
  --device int8_gemv=gemmini --device lm_head_gemv=gemmini \
  --mem-bytes-per-cycle 8.0
```

| scenario | 舊 roofline (16 B/c) | 新 roofline (8 B/c) |
|---|---:|---:|
| decode cycles/token | 79.76M | 157.43M |
| decode tokens/s | 12.537 | **6.352** |
| prefill cycles/token | 4.35M | 4.77M |
| prefill tokens/s | 229.746 | **209.620** |

Decode 幾乎全被記憶體頻寬壓低的 roofline 拖著走（`int8_gemv`、`lm_head_gemv`
都是 memory-bound），所以 decode roofline tok/s 幾乎腰斬（12.537 -> 6.352，
0.507x）；decode headroom 因此從 2.0x 收斂到 ~1.0x — round3 的實測值本來就
非常接近真正的（修正後）記憶體地板，代表 int8_gemv/lm_head_gemv 已經沒有
「以為還有的」2 倍優化空間了。prefill 受影響小很多（4.35M -> 4.77M，
229.746 -> 209.620，0.912x），因為 prefill 的 `int8_gemm` 主體本身是
compute-bound（compute floor 3.80M 未變），只有 memory-bound 的
`lm_head_gemm`（未量測、以 roofline x4 估）與 `silu_mul` 這類項目的 roofline
分量翻倍。以下所有表格中的 `roofline` 欄位已直接改成新（8 B/cycle）數值；
本節保留新舊對比作記錄。

## (c) Round3 vs round2 speedup

- **Decode: 1.007x** tok/s (6.213 -> 6.258 tok/s; 160.94M -> 159.80M cyc/token).
- **Prefill: 1.048x** tok/s (148.916 -> 156.006 tok/s; 6.72M -> 6.41M cyc/token).

Decode barely moved again, for the same structural reason as round2: its two
dominant kernels (`int8_gemv` 76.9% of decode cycles, `lm_head_gemv` 17.9%)
are DMA-bound GEMVs. `int8_gemv`'s own n1 measurement is now flat at 132,424
(round3's search found nothing better across 12 attempted iterations split
over two runs). `lm_head_gemv`'s ratio-scaled entry moved from 118,142 to
113,978 (a further 3.5% cut) because the *dedicated* lm_head tile kernel
improved from 659,142 to 635,908 cycles — but that only buys 1.10M cyc/token
end-to-end (17.9% share) once multiplied by the 128,256-row lm_head, so decode
overall moved just 0.7%.

Prefill moved noticeably more (4.8%) because `int8_gemm` — untouched since
round0 — finally got optimized this round (1.056x faster) and it is the
single largest prefill kernel (62.8% share at round3), on top of `silu_mul`'s
continuing gains (1.153x this round).

## (d) Biggest remaining gap to roofline

**Decode: `int8_gemv`, unchanged from round2, but the gap shrank hugely once
the 2026-09-09 roofline fix landed.** At round3 it still costs 122.89M
cyc/token; against the corrected 121.86M roofline (8 B/cycle mbus) that is
only a ~1.0M-cycle (1.01x) gap — down from the 62M-cycle (2.0x) gap the stale
16 B/cycle assumption implied. Round3 spent 12 iterations across two runs
(`20260908-202413-e8e8` aborted at 4/12 by a session-limit 429, restarted as
`20260909-052323-9d90` for the remaining 8) and found nothing below the
round2 value of 132,424 cycles/call. It remains DMA-bound (~7.92 B/cycle of
the *real* 8 B/cycle mbus peak, ~99%), not compute-bound (the 16x16 Gemmini
array is still ~97% idle at N=1). With the roofline now correctly reflecting
the 8 B/cycle mbus, this kernel is essentially at its floor already — further
gains need batching decode GEMVs (more useful compute per byte moved), not
more per-kernel tuning at N=1; the naive-tiling search itself has converged,
same conclusion as round2.

**Prefill: `lm_head_gemm`, now the largest single gap after the roofline
fix (still an *unmeasured* roofline-x4 placeholder, 1.03M cyc/token vs a
514.03k roofline — a ~0.52M-cycle gap) — larger than `int8_gemm`'s (62.8%
share, 4.03M cyc/token vs a 3.80M roofline, 1.06x the floor, ~0.23M-cycle
gap, unaffected by the memory-bus fix since it is compute-bound).**
Measuring the real `lm_head_gemm` kernel (prefill emits logits for one
position per pass; currently costed as `TODO: same as lm_head_gemv`) is now
the single highest-value remaining gap in prefill.

### lm_head_gemv_gemmini conversion (round2 -> round3)

Same method as round2 (see `projection_round2.md`'s "lm_head_gemv_gemmini
conversion" section for the full rationale): `llama_project.py` extrapolates
`lm_head_gemv_gemmini` linearly in MACs from its measured tile
(`work_measured=1,048,576` MACs, the M=512/K=2048 `n1` shape) up to the full
128,256x2,048 lm_head, so the dedicated lm_head-tile kernel's raw cycle count
(a *different* tile shape, M=2048/K=2048) cannot be substituted directly
without breaking that basis's self-consistency.

Round3 re-optimized the dedicated lm_head tile kernel
(`llama-q8-gemv-gemmini-lmhead`, run `20260908-202428-217e` aborted at 3/8 by
a session-limit 429, restarted as `20260909-052338-b80e` for the remaining 5
iterations): baseline 740,101 -> optimized 635,908 cycles (0.859218x, i.e.
1.164x faster than baseline, 1.037x faster than round2's 659,142).

As in round2, we carry the same fixed round1 n1-basis value (132,653 cycles
at 1,048,576 MACs) forward, scaled by round3's own lm_head-tile improvement
ratio:

```
ratio  = 635,908 / 740,101 = 0.859218
round3 = 132,653 * 0.859218 = 113,978 cycles   (at work_measured = 1,048,576)
```

The raw M=2048 tile numbers (740,101 baseline, 635,908 optimized) and the
round1/round2 history are kept in the entry's `additional_measurements` for
reference; they are documentation only and are not read by
`llama_project.py` (`MeasuredDB.load` keys one `Measurement` per kernel name,
matched against this entry's own `work_measured`/shape).
