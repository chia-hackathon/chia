# Llama-3.2-1B round2 projection vs round1 / round0 / roofline

Generated by `loop/llama_project.py` against three measured-cycle DBs
(`measured_cycles.json` = round0, `measured_cycles_round1.json`,
`measured_cycles_round2.json`), all with
`--device int8_gemv=gemmini --device lm_head_gemv=gemmini` (the GEMV path
this project has used since round1: Gemmini is 4.1-4.7x faster than the
naive Saturn RVV baseline for the N=1 decode GEMV; see the `_README` in the
measured-cycles JSON). Raw command output for all six runs is under
`out/llama-profile/proj_round{0,1,2}_{decode,prefill}.txt`.

Cost basis: **round0** = pristine naive-RVV/Gemmini baselines (`measured_cycles.json`).
**round1** = first optimization pass (`measured_cycles_round1.json`).
**round2** = second optimization pass, this report (`measured_cycles_round2.json`).
**roofline** = `max(compute, memory)` lower bound, no fudge factor.

## (c) Round2 vs round1 speedup

- **Decode: 1.029x** tok/s (6.040 -> 6.213 tok/s; 165.56M -> 160.94M cyc/token).
- **Prefill: 1.077x** tok/s (138.334 -> 148.916 tok/s; 7.23M -> 6.72M cyc/token).

Decode barely moved because its two dominant kernels (int8_gemv 76.4% of
decode cycles, lm_head_gemv 18.4%) are DMA-bound GEMVs that round2 could only
nudge (int8_gemv: 132,653 -> 132,424, +0.2%) or partially improve via the
lm_head-tile-ratio conversion (see below). Prefill moved more because its
gains (silu_mul 1.87x, attn_scores 1.04x) are a bigger share of a much
smaller total.

## (d) Biggest remaining gap to roofline

**Decode: `int8_gemv`.** At round2 it costs 122.89M cyc/token against a
60.93M roofline — a 62M-cycle (2.0x) gap that is *larger by itself* than the
entire rest of the decode budget combined. It is DMA-bound (round2 sustains
~7.92 B/cycle of the 16 B/cycle assumed peak, 49.5%), not compute-bound (the
16x16 Gemmini array is ~97% idle at N=1 because a GEMV can't fill a 16-wide
output). Amdahl sensitivity on the round2 decode projection: even an
infinitely fast `int8_gemv` only buys 4.23x end-to-end, because `lm_head_gemv`
(18.4% share) becomes the next wall. Closing this gap needs either batching
decode GEMVs (N=16 is "nearly free" per the round1 `_README` notes: 12% more
cycles for 16x the MACs) or raising the assumed memory bandwidth, not further
inner-loop tuning of the N=1 kernel.

**Prefill:** no single kernel dominates the 2.37M-cycle gap the way
`int8_gemv` does in decode; it's spread across `int8_gemm` (~0.46M),
`lm_head_gemm` (~0.77M, still an *unmeasured* roofline-x4 placeholder),
`silu_mul` (~0.51M) and `attn_scores` (~0.20M). `int8_gemm` is the single
largest contributor and, like decode's GEMVs, is memory/DMA-bound.

### lm_head_gemv_gemmini conversion (round1 -> round2)

`llama_project.py` extrapolates `lm_head_gemv_gemmini` linearly in MACs from
its measured tile (`work_measured=1,048,576` MACs, the M=512/K=2048 `n1`
shape) up to the full 128,256x2,048 lm_head. Round2 also directly measured,
for the first time, a *dedicated, bigger* lm_head tile kernel
(`llama-q8-gemv-gemmini-lmhead`, M=2048/K=2048, 4,194,304 MACs / 4 MiB of
weights): baseline 740,101 -> optimized 659,142 cycles (0.8906x, i.e. 1.123x
faster).

Substituting 659,142 directly into the entry would break self-consistency,
because that entry's `work_measured`/shape is pinned to the *n1* (M=512)
basis that `llama_project.py`'s MAC-linear scaling depends on — the M=2048
tile has a different fixed/DMA-warmup-to-payload ratio, so its raw cycle
count is not proportional at the n1 work scale. Instead we carried the
round1 n1-basis value (132,653 cycles at 1,048,576 MACs) forward, scaled by
the lm_head tile's own measured improvement ratio:

```
ratio  = 659,142 / 740,101 = 0.890611
round2 = 132,653 * 0.890611 = 118,142 cycles   (at work_measured = 1,048,576)
```

This keeps the extrapolation basis for the full lm_head unchanged from
round1 while reflecting round2's lm_head-specific (not n1-kernel) speedup.
The raw M=2048 tile numbers are kept in the entry's
`additional_measurements` for reference; they are documentation only and are
not read by `llama_project.py` (`MeasuredDB.load` keys one `Measurement` per
kernel name, matched against this entry's own `work_measured`/shape).
