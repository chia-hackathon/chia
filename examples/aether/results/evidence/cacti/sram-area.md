# AETHER SoC — SRAM macro area (CACTI 7)

> **Read `instance-counts.md` for the totals.** The "Summary" table below sums
> each SRAM *definition* once, which is wrong (e.g. `cc_banks_0_ext` is
> instantiated 8x, the Gemmini scratchpad `mem_ext` 4x) and gives a spurious
> −18%. Weighted by hierarchical instance count the correct result is
> **+0.11%** (45 nm: 3.1522 → 3.1558 mm²), total capacity unchanged at
> 967.8 KiB. The per-macro areas below are correct.

Generated by CACTI 7.0 (HewlettPackard/cacti @ 1ffd8df, 2017-06-19).

Two RTL configs of the same Chipyard SoC (Shuttle RISC-V + Saturn VLEN256/DLEN128 + Gemmini 16x16 int8):

- **control** — memory bus 8 B/cycle (64-bit), 10 SRAM macros

- **WideMbus** — memory bus 16 B/cycle (128-bit), otherwise identical; 9 SRAM macros (the `mem_1_ext` 8192x64 macro is gone)

| 22nm | 0.2423 | 0.1988 | -0.0435 | -17.96% |

> `tag_array_0_ext` (depth 16, width 88 = 176 B) is **excluded from every total**: CACTI 7 reports `ERROR: no valid data array organizations found` for it at all four nodes (the array is below CACTI's minimum modelable size). It is identical in both configs, so it does not affect the delta. No analytical fallback was substituted.


130 nm (the `cacti_runner.py` default `technology_um=0.130`) **cannot be run**: CACTI 7 aborts with `Feature size must be <= 90 nm`. 90 nm is the coarsest supported node.

## Limitations (must be stated in the paper)

1. **SRAM macros only.** These numbers cover the 10 / 9 SRAM arrays that Chipyard's
   FIRRTL elaboration emits into `.top.mems.conf`. They do **not** include any random
   logic (core datapath, Saturn VU, Gemmini PEs, uncore, NoC), register files implemented
   as flops, I/O, or physical-design overhead (power grid, routing channels, macro halos,
   placement whitespace). Total die area will be substantially larger.
2. **CACTI is an analytical model, not synthesis.** CACTI 7 estimates area from a
   parameterized circuit/technology model, not from a real memory compiler, a real PDK,
   or a place-and-route run. Absolute values can differ from a foundry SRAM compiler by
   a large factor; treat them as a *relative* comparison between the two configs.
3. **Technology node.** CACTI 7's ITRS-HP device models support only 90/65/45/32/22 nm.
   130 nm is rejected outright. Results are reported at 90, 45, 32 and 22 nm; pick one
   and state it explicitly.
4. **Multi-port / masked writes are approximated.** Chipyard byte-write masks
   (`mask_gran`) have no CACTI equivalent and are ignored; only the R/W/RW port counts
   from `rename_ports()` are passed to CACTI. Masked SRAMs are therefore modeled as
   unmasked arrays of the same geometry, which understates their real area.
5. **`tag_array_0_ext` is unmodeled** at every node (see note above). The control total
   is therefore missing one 16x88 macro and the WideMbus total the same one.

## Reproduction

```bash
BASE=/share1/saves/max410011/hackathon/aether/out/work/cacti
mkdir -p $BASE/{src,tmp,out}
export TMPDIR=$BASE/tmp

# 1. CACTI 7
cd $BASE/src && git clone --depth 1 https://github.com/HewlettPackard/cacti.git
cd cacti && make -j8          # produces ./cacti

# 2. SRAM lists straight out of the elaborated RTL
G=/home/ray/chipyard/sims/verilator/generated-src
for C in GENV256D128GemminiShuttleConfig GENV256D128GemminiShuttleWideMbusConfig; do
  docker exec aether-coexist cat \
    $G/chipyard.harness.TestHarness.$C/chipyard.harness.TestHarness.$C.top.mems.conf \
    > $BASE/$C.mems.conf
done

# 3. Characterize (uses chia.chipyard.macrocompiler.parse_mems_conf +
#    chia.vlsi.sram_cacti.cacti_runner.run_cacti, Ray decorator bypassed)
~/.conda/envs/chia_env/bin/python $BASE/run_area.py 0.090 0.045 0.032 0.022
~/.conda/envs/chia_env/bin/python $BASE/mkreport.py
```

Artifacts:
- `$BASE/run_area.py` — driver
- `$BASE/out/results.json` — machine-readable per-macro results
- `$BASE/out/raw/<node>/<config>/<sram>.{cfg,out}` — the exact CACTI input and full stdout for every run
- `$BASE/*.mems.conf` — the elaborated SRAM lists (evidence)
