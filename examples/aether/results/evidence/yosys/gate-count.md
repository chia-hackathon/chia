# Gate / flip-flop count comparison: control vs WideMbus

Open-source Yosys, no PDK, no area (µm²) numbers. Purpose: quantify how much
widening the memory bus (8 B/cycle -> 16 B/cycle) changes the SoC's
random-logic size, at the RTL generic-cell level.

- **control**  = `GENV256D128GemminiShuttleConfig`
- **WideMbus**  = `GENV256D128GemminiShuttleWideMbusConfig`
- Top module synthesized: **ChipTop** (instantiates `DigitalTop`; confirmed
  clean of any TestHarness/Sim*/DPI references)
- Yosys: `Yosys 0.69+117 (git sha1 e8db64c60-dirty, Release, Clang 21.1.8)`,
  from the YosysHQ `oss-cad-suite-linux-x64-20260922` release tarball
  (conda-forge install was tried first but its dependency solve stalled for
  >10 min and was abandoned in favor of the prebuilt tarball).
- Frontend: `read_slang` (yosys-slang plugin), not the built-in
  `read_verilog -sv`, which errored on a SystemVerilog assignment-pattern
  construct emitted by firtool/CIRCT (`TLError.sv:91`) before ever reaching
  the design's real RTL.
- SRAM `*_ext` macros are true RTL blackboxes in the source (their module
  bodies don't exist anywhere in `gen-collateral/*.sv`); their port lists
  were extracted from `<config>.top.mems.v` (the Verilator-only behavioral
  memory model) into a `(* blackbox *)` stub file so `hierarchy`/elaboration
  resolves, but they contribute **zero** cells/FFs to the counts below.
  Their area was already characterized separately with CACTI.

## Headline numbers

`stat -top ChipTop` immediately after `read_slang` elaboration (the plugin
fully elaborates/flattens the hierarchy into one module, so this *is* the
generic-cell gate/FF netlist -- see Caveats for why the heavier
`synth -flatten` recipe was not used).

| Metric | control | WideMbus | delta | delta % |
|---|---:|---:|---:|---:|
| Total cells (incl. SRAM blackbox instances) | 261,207 | 261,295 | +88 | +0.034% |
| FF instances (`$dff`+`$aldff`) | 18,230 | 18,238 | +8 | +0.044% |
| **FF bits** (width-summed) | 512,474 | 510,317 | -2,157 | **-0.42%** |
| Combinational-gate instances | 242,171 | 242,251 | +80 | +0.033% |
| **Combinational-gate bits** (width-summed) | 5,382,914 | 5,361,760 | -21,154 | **-0.39%** |
| Latch instances (`$dlatch`) | 1 | 1 | 0 | 0% |
| Memory-port cells (`$memrd_v2`/`$memwr_v2`, 128 internal `$mem` objects) | 778 | 778 | 0 | 0% |
| SRAM blackbox (`*_ext`) instances | 27 | 27 | 0 | 0% |

"Instances" = number of generic-cell objects; "bits" = instance count
weighted by each cell's output width (from `stat -width`), a closer proxy
for actual gate/FF area than raw instance count.

**Bottom line: widening the memory bus from 64-bit to 128-bit changes the
SoC's random-logic size by roughly 0.03-0.4% at the generic-cell level** --
essentially a rounding error against the ~261K-cell / ~512K-FF-bit design.
The Saturn core, Gemmini, L2/coherence, and TileLink bus fabric proper are
untouched (identical instance counts, see breakdown below); the entire delta
is localized to a handful of SRAM bank read-address pipeline registers.

## FF breakdown by hierarchical origin (best-effort)

`$dff`/`$aldff` cell names retain their full FIRRTL/Chisel hierarchical
instance path after elaboration (e.g.
`system.tile_prci_domain....gemmini.ex_controller...`), so FF instances were
bucketed by top-level path substring. (Purely combinational cells mostly get
anonymous names like `$procmux$67259` after elaboration and could **not**
be reliably attributed this way -- see Caveats.)

| Submodule (best-effort) | control | WideMbus | delta |
|---|---:|---:|---:|
| Gemmini (accelerator) | 9,439 | 9,439 | 0 |
| Saturn core (scalar+FP+vector, excl. Gemmini) | 3,738 | 3,738 | 0 |
| L2 / coherence (`coh_wrapper`) | 923 | 923 | 0 |
| System/Mem/Periph/Front bus (`sbus`/`mbus`/`pbus`/`fbus`/`cbus`) | 1,195 | 1,195 | 0 |
| Serial TL link | 699 | 699 | 0 |
| Debug module (`tlDM`) | 418 | 418 | 0 |
| Tile infra (prci/buffer/clock, outside core/gemmini) | 1,335 | 1,335 | 0 |
| Other / top-level glue | 483 | 491 | **+8** |
| **Total** | **18,230** | **18,238** | **+8** |

The entire +8 FF-instance delta was traced to 8 new cells named
`system.bank.ram.r_8` .. `r_15` -- SRAM read-address pipeline registers for
an additional memory bank. This matches the SRAM-macro diff: control has 10
distinct `*_ext` blackbox module types (incl. `mem_1_ext`, 27 instances
total split 4/8/1/1/1/2/1/4/4/1), WideMbus has 9 types with no `mem_1_ext`
but one more `mem_ext` instance (4->5, still 27 instances total: split
4/8/1/1/1/2/**5**/4/1). I.e. the wider bus causes the memory generator to
re-partition one scratchpad/cache SRAM into a different bank layout
(same total capacity), not to add real logic elsewhere.

## What was excluded from synthesis

`<config>.top.f` (as generated by the Chipyard/firtool build, 745/744
files) already excludes everything sim/testbench-only; it was used verbatim
plus the SRAM blackbox stub file. Confirmed excluded:
- `TestHarness.sv` (top testbench wrapper) and everything only reachable
  from it (`SimDRAM.v`/`.cc`, `SimJTAG.v`/`.cc`, `SimTSI.v`/`.cc`,
  `SimUART.v`/`.cc`, `mm.cc`, `mm_dramsim2.cc`, `testchip_htif.cc`,
  `testchip_tsi.cc`, `remote_bitbang.cc`, `uart.cc` -- all DPI/C++ sim
  models, never even copied into the yosys work dir).
- No SVA (`assert/cover/assume property`), no `interface`/`package`/`bind`
  constructs were found anywhere in `gen-collateral/`, so nothing needed to
  be dropped for parsing reasons.
- `plusarg_reader.v` was **included** (real synthesizable module) with
  `-D SYNTHESIS` passed to `read_slang`, which selects its synthesizable
  branch (`assign out = DEFAULT`) instead of the sim-only `$value$plusargs`
  branch.
- The recursive `split_*_ext` bit-sliced leaf modules inside
  `<config>.top.mems.v` (a Verilator behavioral RAM model, `reg [W:0] ram
  [0:N]` + always-block) were **not** used at all; only the 9-10 top-level
  `*_ext` module port headers were extracted as blackbox stubs (see above).

## Caveats

1. **No PDK, no area (µm²).** These are generic-cell (`$dff`, `$and`,
   `$mux`, ...) counts from Yosys's RTLIL, not a real standard-cell netlist.
   They are appropriate for a same-methodology relative comparison
   ("X% more/less logic"), not for absolute gate-equivalent or area claims.
2. **`read_slang` fully elaborates/flattens the hierarchy** into a single
   `ChipTop` RTLIL module (the plugin has no keep-hierarchy option), so a
   true per-submodule `stat -top <submodule>` breakdown is not available.
   The FF breakdown above is a best-effort attribution from surviving
   hierarchical cell *names*, not a module-boundary count; combinational
   cells could not be attributed the same way because most lose their
   hierarchical name during elaboration (anonymous `$procmux$N` etc.).
3. **The heavier `synth -top ChipTop -flatten -run coarse:fine` recipe (plus
   `abc -g AND,NAND,OR,NOR,XOR,XNOR,MUX` gate-normalization) was attempted
   first** but its `CHECK pass (checking for obvious problems)` step hung
   for >9 minutes with zero log progress and 100%+ CPU on this
   ~261K-cell / ~10M-wire-bit flat netlist on the shared host, and was
   killed (see `logs/synth_control_heavy_synth_killed.log` /
   `logs/synth_widembus_heavy_synth_killed.log`). Given the time budget, we
   fell back to the pre-optimization `stat`/`stat -width` numbers taken
   directly after `read_slang` elaboration for both configs -- this is still
   a legitimate generic-cell gate count (same abstraction level FIRRTL/CIRCT
   emits) and, critically, **both configs were measured with the identical
   recipe**, so the relative delta is apples-to-apples even though it is
   not ABC-technology-mapped/optimized. Absolute cell counts would likely
   shrink significantly under a real `synth`+`abc` flow (constant folding,
   CSE, mux/adder sharing), but there is no reason to expect it would change
   the *relative* delta between the two configs materially, since the
   change (SRAM bank repartitioning) is highly localized.
4. **Internal `$mem` objects (128 of them, 66,934 / 68,078 bits) and their
   778 read/write port cells** are reported separately and excluded from
   both the FF and combinational-gate totals -- they are small Chisel
   `Mem`/`SyncReadMem` register files that Yosys has not yet decomposed into
   FFs+muxes at this stage (that decomposition normally happens inside
   `synth`'s `memory` pass, which was skipped per caveat 3). They are
   identical (128/128) between configs, only their bit-width differs
   slightly (66,934 vs 68,078 memory bits -- consistent with the same
   bank-repartitioning noted above).
5. Runtime: environment setup (oss-cad-suite tarball download+extract) ~2
   min; each `read_slang` + `stat -width` run ~11-13s per config (well
   within budget; the abandoned heavy-synth attempt ran ~9 min before being
   killed). Peak yosys process memory ~1.5 GB per run; host had >140 GB
   free throughout, never close to exhaustion.

## Reproduce

```
WORK=/share1/saves/max410011/hackathon/aether/out/work/yosys
YOSYS=$WORK/oss-cad-suite/bin/yosys
nice -n 19 $YOSYS -s $WORK/scripts/synth_control.ys     # or synth_widembus.ys
```
Scripts/logs/outputs all live under this directory:
- `scripts/synth_{control,widembus}.ys` -- main run (read_slang + stat)
- `scripts/stat_width_{control,widembus}.ys` -- same, with `stat -width`
- `scripts/list_dffcells_{control,widembus}.ys`,
  `scripts/list_cells_{control,widembus}.ys` -- cell-name dumps for the
  submodule attribution
- `scripts/make_blackbox_stub.py` -- extracts SRAM `*_ext` blackbox port
  declarations from `<config>.top.mems.v`
- `scripts/summarize.py` -- parses `stat -width` output into FF/comb
  bit & instance totals
- `scripts/categorize_ff.py` -- best-effort hierarchical bucketing
- `out/{control,widembus}/*.generic_stat*.txt` -- raw yosys `stat` output
- `logs/` -- full run logs, including the abandoned heavy-synth attempt
