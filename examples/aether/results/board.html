round9 的 llama-layer-fused-n1 之所以能疊出 13.2% 的縮減，是因為這顆 kernel 自身的 Saturn 裝置佔比高達 13.8%（28,372/206,304）——有足夠大的非 Saturn 工作量可以疊在它旁邊。llama-lmhead-fused-n1 完全不同：iter1 量到的序列化 Saturn 工作（rms+quant+argmax = 12,772 cycles）只佔整個 printf-free iteration 總量（647,593）的 1.97%——比 round9 kernel 自己的佔比小了一個數量級。critical path 上根本沒有足夠的非 Saturn 工作可以疊，重疊比例外推在算術上就不成立，跟 host 排程調得多細都無關。

三組 PROBE 的解讀

  • iter1：phase split。把 Saturn 端拆成 rms／quant／argmax 三段分別計時，序列化總和 12,772 cycles，確認這顆 kernel 能疊的量本來就很小（1.97%）。
  • iter3：held_* 探針，27,151 遠大於 12,772。照理交錯排程應該把 Saturn 成本部分藏進權重串流，量到的暴露量卻反而比序列基準還大超過一倍。最可能的解釋：交錯排程把相鄰的 Saturn phase 在權重串流中拉開約 16K-block（530 KiB），超過 512 KiB 的 L2 容量，導致 X／xn／LG 在兩次造訪之間被逐出——每個 phase 的第二次造訪（rms2、amax2）從 L2 命中變成 DRAM 冷抓取，把 held 時間吃到遠超過原本的序列成本。
  • iter4：spin-wait 掃描。在 spin 週期 0/80/250/600 之間掃描，period_sum（154,598 / 154,376 / 150,380 / 145,647）隨 spin 週期遞減，只顯示出約 109 cycle 的淨隱藏下限——是個結構性的地板，不是排程沒調好，整體 iteration 仍以 698,428 未能回到 648,292 baseline。

13,785 與 12,772 的對齊。round10 前期估算曾用 13,785（648,292 融合 baseline − 634,507 round4 GEMV-only 最佳，同一權重串流）作為重疊的理論上限，跟 iter1 探針量到的 12,772 對不起來，一度被記為「無法從單一 PROBE 行重建、待釐清」。out/llama-profile/projection_round10.md 末尾（2026-09-18 新增一節）已釐清：兩者量的是不同東西，都對。12,772 是 rms+quant+argmax 三段 Saturn phase 本身的序列成本，是原則上可以被藏住的量；13,785 是把同一件事對到 baseline（而非 probe build）算出的上限，多出的 ~700–1,000 cycles 來自冷 L2 罰時與 fence（648,292 − 634,821 = 13,471，加上探針總量 647,593 與 baseline 之間的差額）。兩個數字都正確，實測結果是兩者皆未被藏住——重疊比例是 0。

累計結果（loop 全部結束，smoke + round1–10）：63 runs、248 iterations、$180.16、約 73 h 58 m（~74 小時）wall clock。整體最佳成果仍是 llama-layer-fused-n1 的 179,033（對 206,304 baseline 為 −13.2%，round9），llama-lmhead-fused-n1 以 TERMINAL／負結果收尾（648,292，1.000x，roofline 比 1.218）。10 顆 kernel 的整體幾何平均加速比 2.50×（不含 round10 這顆負結果 kernel 為 2.76×；此前誤植、排除 ACTIVE kernel 又只算 8 顆的 3.08× 已訂正，見 out/paper-submission/README.md 訂正史第 4 條）。

loop 到此收工，下一步是論文。round10 是設計來關閉「單一 kernel 量到的重疊比例可否外推到別的 kernel family／shape」這個效度威脅的實驗，結果乾淨且明確：不可以，且原因（Saturn 佔比差一個數量級、交錯排程反而製造 L2 冷抓取）已用三組 PROBE 交叉驗證，不是量測雜訊或排程沒調好。不再投入新的 iteration；剩下的工作是把 11 輪、63 runs、248 iterations、三次訂正歷史寫成 4 頁論文（out/paper-submission/）。

實作方式：兩個 config fragment 與驗證方法

  • 加寬 memory bus — WithAetherMemoryBusWidth(bits) 覆寫 freechips.rocketchip.subsystem.MemoryBusKey 的 beatBytes。rocket-chip 預設 beatBytes = 8，AETHER 的 config chain 從未覆寫過它；WithSystemBusWidth(128) 只動 SystemBusKey，跟 mbus 無關。AXI4 mem port 與 testchipip 的 SimDRAM 都跟著 MemoryBusKey.beatBytes 走，不需要另外改。
  • 加深 L2 MSHR 檔 — WithAetherL2MemCycles(cycles) 覆寫 InclusiveCacheKey 的 memCycles；MSHR 數是推導出來的，all_mshrs = 2 + max(2, ceil(memCycles / blockBeats))，memCycles=40 給 12（control），memCycles=88 給 24。兩個 fragment 都必須放在 chipyard.config.AbstractConfig 左邊才能生效覆寫。
  • 驗證參數真的生效（從產生的產物驗證，不只是相信 rc=0）：生成的 .dts 裡 sifive,mshr-count 依序是 12 / 12 / 24 / 24；生成的 TestHarness.sv 裡 SimDRAM 的 .DATA_BITS() 依序是 64 / 128 / 64 / 128 位元——確認 AXI4 mem port 與 DRAM 模型都真的跟著 mbus 寬度走。四個設計點 elaborate 全部 rc=0；原本的 control config 未被改動，hwconfig.self_test() 仍 PASS。
  • 限制：只測了兩個 kernel（都是記憶體受限的 GEMV）；只測了 8/16 B/cycle 兩點，沒有 32 B 的點；沒有做中間 MSHR 值的掃描（只有 12/24 兩點）；模擬器用的是零額外延遲的 mm_magic_t DRAM 模型（+dramsim 從未被傳入），所以這是「鏈路寬度」實驗，不是真實 DRAM 時序實驗；沒有面積或功耗數據，不是完整 Pareto 前緣。
